### ADR-0007 메인 스레드 검사는 플랫폼이 주입한 검사기로 생명주기 진입점에서 한다
- 상태: 채택
- 날짜: 2026-11-10
- 배경: ADR-0005는 생명주기 호출을 단일(메인) 스레드로 제한하면서, 잘못된 스레드 호출은 컴파일러가 잡지 못하므로 필요하면 검사를 추가한다고 남겼다. M2에서 Swift 6 뷰가 `@preconcurrency`로 Kotlin 뷰 계약을 채택하면서, 메인이 아닌 곳에서 뷰를 부르면 iOS는 런타임에 크래시하고 Android는 크래시하거나 조용히 경쟁 상태가 생긴다는 점이 드러났다. 두 플랫폼에서 같은 지점, 같은 메시지로 실패시키려면 공유 코드가 검사해야 한다. 하지만 `commonMain`에는 현재 스레드가 메인인지 알 수 있는 표준 API가 없다.
- 결정: 공유 코드에 `fun interface MainThreadChecker`와 설정 지점 `RibThreadingConfig.mainThreadChecker`(기본값 null)를 둔다. 플랫폼은 앱 시작 시 검사기를 넣는다. `Router`의 `dispatchAttach`·`dispatchDetach`·`attachChild`·`detachChild`는 검사기가 있으면 메인 스레드인지 `check`로 확인한다. 뷰 계약 호출처럼 프레임워크가 가로챌 수 없는 지점에서는 `checkMainThread(operation)`을 직접 부른다.
- 고려했던 대안:
  (1) 문서 규칙만 두기: 원본 Uber RIBs와 같은 수준이다. 하지만 실수가 플랫폼마다 다른 증상으로 늦게 드러나서 기각했다.
  (2) `expect fun isMainThread()` + 플랫폼별 `actual`: 주입이 필요 없다. 하지만 레포 규칙(공유 코드에 expect/actual 금지)과 ADR-0004에 어긋나서 기각했다.
  (3) 생명주기 메서드 안에서 메인 디스패처로 자동 전환: 호출 측이 편하다. 하지만 동기 호출이 비동기가 되어 생명주기 순서가 바뀌고 ADR-0005의 대안 (2)를 기각한 이유와 같아서 기각했다.
  (4) `ViewPresenter`가 뷰 호출을 감싸 메인으로 보내기: 뷰 계약은 앱마다 다른 인터페이스라 프레임워크가 호출을 가로챌 수 없다. 원본 `ViewPresenter`도 뷰를 들고만 있어서 기각했다.
- 결과: 잘못된 스레드 호출이 모든 플랫폼에서 생명주기 진입점에서 같은 메시지로 바로 실패한다. 기본값은 검사하지 않으므로 기존 테스트와 JS 타깃에 영향이 없다. 반면 플랫폼이 검사기를 넣지 않으면 보호되지 않고, 뷰 계약 호출은 `checkMainThread`를 부른 곳만 보호된다. 원본에는 없는 확장 API다.
- 관련: ADR-0004, ADR-0005, ADR-0006
