### ADR-0015 401은 저장소 오류 `Unauthorized`로 피처에 올리고, 토큰 갱신은 `BearerTokenTransport`가 한 번만 한다
- 상태: 채택
- 날짜: 2026-11-26
- 배경:
  - ADR-0014 이후 `TodoApiClient`는 401을 `Unauthorized`로 나누지만 `RemoteTodoRepository`가 모든 실패를 `Unavailable`로 줄였다. 피처는 토큰이 만료돼도 "불러오지 못했습니다"와 다시 시도 버튼만 보여 줬고, 다시 시도해도 같은 401이 났다.
  - `BearerTokenTransport`는 토큰 갱신과 401 뒤 재전송을 하지 않았다. 실제 앱은 수명이 짧은 접근 토큰과 갱신 토큰을 함께 쓰는 경우가 많다.
  - carti-RIBs-Swift는 ADR-0036으로 같은 일을 했다. 이 결정은 그 동작 규칙을 따르고 구현만 코루틴에 맞춘다. (이슈 #6의 4번)
- 결정:
  - `TodoRepositoryException.Unauthorized`를 더한다. `RemoteTodoRepository`는 API의 `Unauthorized`만 이것으로 바꾸고, 나머지 실패는 여전히 `Unavailable`이다(403도 `Unavailable`).
  - `TodoInteractor`는 `Unauthorized`를 받으면 오류 문구 없이 로딩만 끄고 `TodoListener.didRequireSignIn()`으로 부모에게 넘긴다. `RootInteractor`는 이것을 로그아웃과 같은 경로(`didRequestLogout`)로 보낸다.
  - `BearerTokenTransport(inner, token, refresh)`를 더한다(`refresh` 없는 생성자는 그대로). 토큰을 붙여 보낸 요청이 401을 받으면:
    - 지금 `token()`이 거절된 토큰과 다르면 갱신하지 않고 지금 토큰으로 다시 보낸다(다른 요청이 이미 갱신했다).
    - 아니면 `refresh()`를 부른다. 갱신은 `Mutex`로 한 번에 하나만 돌고, 동시에 401을 받은 요청은 그 결과를 기다린 뒤 바뀐 토큰으로 다시 보낸다.
    - 갱신이 null이면 원래 401을 돌려준다. 같은 토큰으로 기다리던 요청은 다시 갱신하지 않고 401을 돌려준다.
    - 다시 보내는 것은 한 번뿐이다. 또 401이면 그대로 돌려주고 `TodoApiClient`가 `Unauthorized`로 알린다.
    - 토큰 없이 보낸 요청의 401, 401이 아닌 상태(403 등)는 갱신하지 않는다.
  - 토큰의 원본은 플랫폼 저장소 하나다. `refresh`는 새 토큰을 저장해 이후 `token`이 그 값을 돌려주게 해야 한다. `BearerTokenTransport`는 토큰을 저장하지 않는다.
  - 샘플 앱은 토큰을 발급하지 않는다(로그인은 이름만 받는다). 인증 서버가 없으므로 `MultiFeatureApp`은 `BearerTokenTransport`를 조립하지 않는다. 토큰을 받는 로그인과 저장소는 실제 앱이 이 자리에 넣는다.
- 고려했던 대안:
  (1) `Unauthorized`를 화면 문구로만 보여 주기: 사용자가 직접 로그아웃해야 하고 다시 시도 버튼은 의미가 없다. 로그인으로 돌려보내는 것은 부모의 책임이라 리스너로 올린다. 기각.
  (2) 루트가 저장소를 보고 401을 감지하기: 루트는 저장소를 모른다(ADR-0012). 요청한 피처가 감지하고 부모가 정하는 RIBs의 리스너 방향을 따른다. 기각.
  (3) 리스너 이름을 `didRequestLogout`으로: 지금은 같은 경로지만 "세션이 만료됐습니다" 안내를 띄우려면 원인을 구분해야 한다. 원인으로 이름을 붙인다.
  (4) Ktor `Auth` 플러그인(`bearer { refreshTokens }`): 동시 401 처리까지 제공한다. 대신 인증이 Ktor 전송에 묶여 `HttpTransport` 구현을 바꾸면 사라지고, 위 규칙을 가짜 전송으로 공통 테스트할 수 없다. 기각(ADR-0014의 대안 (1)과 같은 이유).
  (5) 갱신을 분리된 코루틴(앱 범위 스코프)에서 돌리기: 갱신을 시작한 요청이 취소돼도 기다리던 요청을 위해 갱신이 끝까지 돈다(Swift ADR-0036의 동작). 대신 전송이 스코프와 디스패처를 가져야 하고, 디스패처는 `RibDispatchers`로만 고른다는 규칙과 수명 관리가 붙는다. 기각. 갱신을 시작한 요청이 취소되면 갱신도 취소되고, 기다리던 다음 요청이 갱신을 다시 시작한다.
  (6) 갱신 뒤 여러 번 재전송: 새 토큰도 거절되면 서버가 세션을 끊은 것이다. 계속 갱신하면 갱신 엔드포인트를 반복해서 친다. 한 번으로 둔다. 기각.
  (7) 갱신한 토큰을 `BearerTokenTransport`에 저장: 토큰의 원본이 둘이 되어 플랫폼 저장소(키체인 등)와 어긋날 수 있다. 기각.
- 결과:
  - 공통 테스트(`BearerTokenRefreshTest`)가 갱신과 한 번의 재전송, 갱신 실패, 토큰 없는 요청, 403, `refresh` 없음, 동시 401의 갱신 하나, 늦게 온 옛 토큰의 401, 동시 요청의 갱신 실패 공유를 JVM·JS에서 확인한다. 두 분기(바뀐 토큰 재사용, 실패 공유)를 일부러 빼면 해당 테스트가 실패하는 것을 확인했다.
  - 흐름 테스트가 401 → 오류 문구 없이 로그인 화면, 할 일 RIB 분리를 확인한다. 웹 Vitest는 테스트 서버의 401로 같은 흐름을 확인한다.
  - `Mutex`는 여러 요청 코루틴이 함께 쓰는 데이터 계층 상태에만 쓴다. 생명주기 메서드에는 락을 두지 않는다는 ADR-0005와 범위가 다르다.
  - 쓰기 요청(`createTodo`)의 401은 아직 피처까지 오지 않는다. 쓰기를 쓰는 피처가 생기면 같은 저장소 오류를 쓴다.
  - iOS는 Mac에서 확인하지 않았다. 바뀐 Swift 코드는 없다.
- 관련: ADR-0005, ADR-0012, ADR-0014, 이슈 #6, carti-RIBs-Swift ADR-0036
