### ADR-0011 샘플 플랫폼 뷰는 순수 뷰와 어댑터로 나눈다
- 상태: 채택
- 날짜: 2026-11-25
- 배경: Android·iOS 샘플은 한 타입(또는 한 파일)이 뷰 계약(`XxxViewContract`) 구현과 그리기를 같이 맡는다. 그리기 코드가 계약 타입·상태 타입·리스너를 직접 참조해서, Compose Preview나 단독 테스트를 하려면 공유 모듈 타입을 같이 준비해야 하고, iOS 뷰에는 Kotlin이 내보낸 타입이 섞인다. 웹(ADR-0009)은 Kotlin 어댑터와 React 뷰가 이미 나뉘어 있다. (이슈 #4)
- 결정: 샘플의 플랫폼 뷰를 둘로 나눈다.
  - **순수 뷰**: 값과 콜백만 받아 그린다. 공유 모듈(`login-shared`, `-api`)과 `ribs-*` 어댑터 모듈을 import하지 않는다. 새 인터페이스나 기반 클래스를 두지 않는다. 입력 중인 텍스트·포커스처럼 공유 코드에 알릴 필요 없는 화면 지역 상태는 순수 뷰가 가진다(`rememberSaveable`, `@State`).
  - **어댑터**: `XxxViewContract`를 구현하고 받은 상태를 순수 뷰 인자로 풀어 넘긴다. `ComposeRenderable`/`SwiftUIRenderable` 채택, 리스너 호출, 자식 화면 슬롯 연결, Kotlin 타입 변환을 맡는다.
  - 어댑터는 플랫폼 앱 안에 둔다. 의존 방향은 어댑터 → 순수 뷰, 어댑터 → 공유 모듈이고, 순수 뷰와 공유 모듈은 서로를 모른다.
  - 라이브러리(`ribs-core`, `ribs-compose`, `ribs-web`, `RIBsKMPSwiftUI`)는 바꾸지 않는다.
- 고려했던 대안:
  (1) 현상 유지: 코드가 가장 짧지만 뷰가 계약 타입에 묶여 Preview·단독 테스트·다른 공유 구현(carti-RIBs-Swift)과의 비교가 어렵다. 기각.
  (2) 뷰가 소유하는 인터페이스를 두고 어댑터가 구현: 뷰가 참조 객체를 들어야 할 때만 이득이 있고 화면마다 타입이 하나 더 는다. 기본으로 삼지 않는다.
  (3) 라이브러리에 뷰 기반 타입 추가: 코어가 뷰 모양을 강제하게 되어 ADR-0004와 맞지 않는다. 기각.
- 결과: 순수 뷰는 Preview와 값만으로 그릴 수 있고 iOS 뷰에서 Kotlin 타입이 빠진다. 반면 화면마다 파일이 하나 늘고, 단순 화면의 어댑터는 값을 넘기기만 한다. 순수 뷰 인자 목록은 플랫폼마다 따로 적는다. 자식 화면 슬롯을 순수 뷰에 넘기는 방식은 첫 화면 이후 정한다.
- 관련: ADR-0004, ADR-0006, ADR-0009, 이슈 #4
